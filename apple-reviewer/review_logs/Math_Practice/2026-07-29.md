### 提案1: 匿名ユーザーに「購入を復元」ボタンが表示されない
- 種別: 問題のある設計の修正要求
- 対象: `lib/ui/screens/settings/settingsScreen.dart`（1238〜1297行付近、「アカウント管理」カード内 1268〜1281行の「購入を復元」ListTile）
- 内容: 「購入を復元」ListTileが、`FirebaseAuth.instance.currentUser != null && !FirebaseAuth.instance.currentUser!.isAnonymous` という条件で描画される「アカウント管理」カードの内側に置かれている。このカード自体はファイル冒頭コメント（11〜13行）にある通り「アカウント削除」機能専用に設計された表示条件（`providerData`が空で再認証できない匿名ユーザーを削除フローの対象外にするため。2026-07-26レビューで削除ボタンのクラッシュ対策として導入）であり、`my_common_templates/data_management/data_storage_pattern.md`の「4. アカウント削除UIの表示条件」に明文化されている自分パターンそのものである。しかし「購入を復元」は削除機能とは無関係な別機能であるにもかかわらず、同じカードに同居しているため、この匿名ユーザー除外条件を意図せず継承してしまっている。
  - コード調査で確認した事実: `purchaseRemoveAds()`（`lib/utils/inAppPurchaseAndReceiptVerificationManager.dart` 106行〜）は`PurchaseAccountLinkService.ensureSignedIn()`（`lib/utils/anonymousPurchaseAccountLinkingService.dart`）で匿名サインインのみを行い購入を完了させる設計であり、Cloud Function `verifyPurchase`（`functions/src/index.ts` 109〜126行）も`request.auth`の有無のみをチェックし`isAnonymous`は一切見ていない。つまり技術的には匿名uidのまま購入・検証とも完結しており、復元だけを非匿名ユーザーに限定する技術的必然性はない。
  - 実害シナリオ: `apps/Math_Practice.md`にある通り本アプリは匿名購入運用（`anonymousPurchaseAccountLinkingService.dart`）を採用しており、Google/Apple連携をせず匿名のまま非消耗型「広告削除」（`com.zetaiw.math100.removeads`）を購入したユーザーが、機種変更・再インストールで新しいFirebaseセッションになった場合、「購入を復元」ボタン自体が画面に出ないため正当な購入を復元する手段が無くなる。
- 根拠:
  - Apple公式ルール: `apple_guidelines/03_business/iap_rules.md`「4. プロダクト種別の正しい分類」（非消耗型は復元処理が前提）、`in_app_purchase/restore_purchase_flow.md`「1. 復元ボタンの設置」（設定画面または購入画面に復元ボタンを必ず設置する）
  - 自分パターン: `my_common_templates/in_app_purchase/iap_implementation_pattern.md`「2. Restore Purchaseの実装方針」（明示的な復元導線を用意する）、`my_common_templates/in_app_purchase/iap_implementation_pattern.md`「4. 未ログイン購入とアカウント連携の標準フロー」（匿名のまま購入が完結する設計であること）、`my_common_templates/data_management/data_storage_pattern.md`「4. アカウント削除UIの表示条件」（今回誤って継承されている条件の本来の適用範囲＝アカウント削除専用であること）
- 提案内容: 「購入を復元」ListTileを「アカウント管理」カード（`!isAnonymous`条件）の外に出し、`Platform.isIOS`のみを条件に、ログイン状態・匿名状態にかかわらず常に表示する（削除ボタンのみ現状の`currentUser != null && !isAnonymous`条件を維持する）。カードを分けるか、UI上「アカウント管理」カードとは別セクションに独立させることを推奨する。

### 提案2: 「購入を復元」実行時にFirebase未サインイン状態だと検証が失敗し、かつUIには成功表示のまま失敗が伝わらない可能性がある（提案1調査中に偶発的に発見）
- 種別: 問題のある設計の修正要求
- 対象: `lib/ui/screens/settings/settingsScreen.dart`の`_restorePurchases()`（1305〜1323行）、`lib/utils/inAppPurchaseAndReceiptVerificationManager.dart`の`_handlePurchaseStreamUpdate()`（151〜186行）・`_verifyPurchaseReceiptOnServer()`（191〜208行）
- 内容: `_restorePurchases()`は`InAppPurchase.instance.restorePurchases()`を呼ぶのみで、購入時の`purchaseRemoveAds()`と異なり`PurchaseAccountLinkService.ensureSignedIn()`を経由しない。ストアからの復元トランザクションは`purchaseStream`経由で`_handlePurchaseStreamUpdate()`が受け取り`_verifyPurchaseReceiptOnServer()`でCloud Function `verifyPurchase`を呼ぶが、この関数も`request.auth`の存在チェックのみで、未サインイン（`currentUser == null`）なら`functions/src/index.ts` 112〜114行の`if (!request.auth) throw new HttpsError('unauthenticated', ...)`で即座に失敗する。
  - 提案1を単に「表示条件を外すだけ」で対応した場合、Firebase Authに一度もサインインしたことがない新規インストール直後のユーザー（＝`currentUser == null`）が復元ボタンを押すと、検証は`unauthenticated`で失敗する。
  - さらに、この失敗は`_restorePurchases()`自身のtry/catchでは捕捉されない（`restorePurchases()`呼び出し自体は例外を投げず、検証失敗は非同期の`purchaseStream`リスナー側で`onError`コールバックに渡るのみ）。そのため`_restorePurchases()`は「復元処理を開始しました。購入済みの場合は反映されます。」という成功メッセージのスナックバーを表示してしまい、実際には`is_premium`が付与されないまま、ユーザーには失敗が伝わらない可能性がある。
- 根拠: `in_app_purchase/restore_purchase_flow.md`「3. 復元失敗時のハンドリング」（復元対象なし・通信エラー等の状態を分かりやすいメッセージで表示する）、`my_common_templates/in_app_purchase/iap_implementation_pattern.md`「4. 未ログイン購入とアカウント連携の標準フロー」（購入の起点は必ず`ensureSignedIn`相当を経由させる、という既存原則の脱漏）
- 提案内容: `_restorePurchases()`の冒頭で`PurchaseAccountLinkService.ensureSignedIn()`（またはそれに相当する匿名サインイン確保処理）を先に呼んでからネイティブの`restorePurchases()`を実行する。あわせて、`_handlePurchaseStreamUpdate()`の`onError`コールバックが確実に設定画面側のエラー表示（`showErrorMessageSnackBar`等）にも伝播するよう、`_restorePurchases()`実行中は検証結果（成功/失敗）を待ってからスナックバーの内容を出し分けることを検討する。

### 提案1: purchase_indexが単一uidしか保持できず、同一Apple ID上の複数Firebaseアカウントが同じ取引を共有した場合に返金剥奪が漏れる

- 種別: 問題のある設計の修正要求
- 対象: `functions/src/index.ts` の `verifyPurchase`（108〜169行目付近）・`handleAppStoreNotification`（240〜330行目付近）・`deleteAccount`（393〜430行目付近）
- 内容:
  `purchase_index/{indexKey}`（iOSは`originalTransactionId`、Androidは`purchaseToken`のSHA-256ハッシュがindexKey）は、`verifyPurchase`成功時に`batch.set(..., { uid, productId, platform, ...extraFields, createdAt })`（mergeオプションなし）で**上書き**される（159〜164行目）。
  `my_common_templates/in_app_purchase/iap_implementation_pattern.md` 4番が要求する「アカウント連携でuidが変わる瞬間に`restorePurchases()`を自動的に呼ぶ」設計（`loginScreen.dart`の`_handlePostSignIn`が`!hasProfile`時に自動実行）そのものは正しい。しかし、同一Apple ID配下で**別のFirebaseアカウントB**が新規サインアップしてこの自動復元を踏むと、Appleは同じ`originalTransactionId`を返すため、`purchase_index/{txId}.uid`が「A」から「B」へ単純上書きされる。
  この結果、`users/A.is_premium = true`は取り残されたまま更新されなくなる。その後Appleがこの取引について返金処理を行うと、`handleAppStoreNotification`（313〜320行目）は`purchase_index`から**単一の`uid`フィールド**（現在は「B」）だけを読んで`users/{uid}.is_premium = false`にするため、**Aのプレミアム権利は返金後も剥奪されずに残り続ける**。
  さらに`deleteAccount`（419〜422行目）は`purchase_index`を`where('uid', '==', uid)`という単一値一致で検索しているため、この上書き構造では「過去に関与したが現在の`uid`フィールドには載っていないアカウント」の逆引きエントリを見つけられず、アカウント削除時のクリーンアップも不完全になる。
  「同一Apple IDで複数のアプリ内アカウントが購入を共有できる」こと自体はApple Guideline 3.1.1の復元機能要件上必須の仕様であり是正対象ではない。是正すべきは「関与した全アカウントを追跡できていない」逆引きインデックスの設計。
- 根拠:
  - [`../../in_app_purchase/restore_purchase_flow.md`](../../in_app_purchase/restore_purchase_flow.md) 2番（機種変更・再インストール後の復元の正常動作）／[`../../refund_cancellation/apple_managed_refund_flow.md`](../../refund_cancellation/apple_managed_refund_flow.md) 1番（返金はAppleが一元管理する一方、アプリ側は返金が確定した権利を確実に反映する責務を負う）
  - [`../../my_common_templates/in_app_purchase/iap_implementation_pattern.md`](../../my_common_templates/in_app_purchase/iap_implementation_pattern.md) 4番（アカウント連携時の自動`restorePurchases()`を要求する設計そのものが、単一uidの逆引きインデックスでは両立しないことが今回判明した）
  - [`../../my_common_templates/data_management/data_storage_pattern.md`](../../my_common_templates/data_management/data_storage_pattern.md) 5番（Cloud Functions専用の逆引き・インデックスコレクションは、そのuidに紐づくエントリをアカウント削除時にも削除対象に含める、という既存原則。今回のケースは「1ドキュメントに複数uidが関与しうる」ケースがこの原則の想定に含まれていなかったことが根本原因）
- 提案内容:
  1. **`verifyPurchase`**: `purchase_index`書き込みを、`uid`単一フィールドの上書きから、`uids`配列フィールドへの`FieldValue.arrayUnion(uid)`に変更する（iOS・Android＝Google Play両方の書き込みパス、159〜164行目付近）。`FieldValue`は5行目で既にimport済み。
  2. **`handleAppStoreNotification`の返金処理**: `purchase_index`から取得するフィールドを`uid`単数から`uids`配列に変更し、配列内の**全uid**それぞれに対して`users/{uid}.is_premium = false`を設定するバッチ処理に変更する（313〜320行目付近）。
  3. **`deleteAccount`のクリーンアップ**: `where('uid', '==', uid)`（419〜421行目）を`where('uids', 'array-contains', uid)`へ変更する。ドキュメントの扱いは以下の方針で確定する（作業エージェントに独自判断させない）:
     - `FieldValue.arrayRemove(uid)`でそのuidだけを配列から取り除く
     - 取り除いた結果、配列が空になった場合のみドキュメントごと削除する
     - 他のuidが配列に残る場合はドキュメントを削除せず、共有元アカウントの将来の返金処理（提案2の全uid剥奪ロジック）に必要な逆引き経路を保持する
     - **判断根拠:** `data_storage_pattern.md`5番は「そのuidに紐づくエントリを削除対象に含める」ことを要求しており、単一uid上書き構造を前提にした表現だが、複数uid共有構造では「そのuid自身のエントリ（＝配列内の要素）」を削除することがこの原則の忠実な適用にあたる。ドキュメント自体を無条件削除すると、削除していない側のアカウント（例: 上記シナリオのB）が将来受け取る返金についてAppleからの通知を紐づけられなくなり、`database_delete_policy.md`が要求する「削除対象範囲の明文化」に反して他アカウントの正当な購入証跡・返金反映経路を壊す実害の方が大きい。したがって「配列が空になるまでドキュメントは残す」を確定方針とする。

## 対応サマリ（作業エージェント記入・レビュー対象アプリ側で追記）

### 提案1への対応
- 状態: 対応済み
- 対応内容:
  レビューサマリの確定方針どおり、`purchase_index/{indexKey}` のスキーマを `uid` 単数から `uids` 配列に変更した。
  1. `verifyPurchase`（159〜173行目付近）: `batch.set(..., { uid, ... })`（mergeなし上書き）を、`batch.set(..., { uids: FieldValue.arrayUnion(uid), ... }, { merge: true })` に変更。iOS・Android共通の書き込みパス（同一`batch.set`呼び出し）に適用済み。
  2. `handleAppStoreNotification` の返金処理（312〜333行目付近）: `purchase_index`から読むフィールドを`uid`単数から`uids`配列に変更し、`db.batch()`で配列内の全uidの`users/{uid}.is_premium`を`false`に設定するよう変更。
  3. `deleteAccount`（418〜436行目付近）: クエリを`where('uids', 'array-contains', uid)`に変更。ドキュメントごとの`uids`配列長を確認し、削除対象uidを除いた残りが0件になる場合のみドキュメントを削除、他のuidが残る場合は`FieldValue.arrayRemove(uid)`で自分のuidのみを取り除きドキュメント自体は残す（確定方針どおり）。
  4. 将来Android有効化時にコメントアウトされている`handleGooglePlayNotification`（未使用・非アクティブ）内のコメント疑似コードも、同じ`uids`配列スキーマに合わせて更新（デプロイ対象外の死んだコードのため動作への影響なし。将来有効化時の設計不整合を防ぐための予防的修正）。
  5. `docs/test_specs/in_app_purchase_and_receipt_verification.md`に、複数Firebaseアカウントによる購入共有時の正常系テストケース（返金で全アカウント剥奪）、およびアカウント削除時のクリーンアップに関する異常系テストケース（単独関与時はドキュメント削除／共有中は自分のuidのみ除去しドキュメント存続）を追記。
  `cd functions && npx tsc --noEmit`で型チェック成功、`flutter analyze`は本件と無関係な既存warning（pubspec.yamlのasset_field、Dart側は無変更）のみで問題なし。`npm run deploy`で`verifyPurchase`・`handleAppStoreNotification`・`deleteAccount`の3関数を本番（asia-northeast1）へデプロイ完了。

  なし。本修正の範囲外の判断が必要な曖昧点には遭遇しなかった。

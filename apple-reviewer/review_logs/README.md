# 審査ログの記録方法

複数アプリを並行してレビューすることがあるため、アプリごとにサブフォルダを分けて記録する。
`review_logs/{アプリ名}/{日付}.md` の形式で保存する。同じアプリを同日中に複数回レビューする場合は `{日付}_2.md` のように連番を付けて既存ログを上書きしない。

## 役割分担とファイル編集権限

このナレッジベース（apple-reviewerフォルダ）を読み込む**審査エージェント**と、実際のアプリのプロジェクトフォルダで作業する**作業エージェント**は役割が異なり、編集してよい範囲も異なる。

- **審査エージェント**（このフォルダを読み込むエージェント）
  - 編集してよいのは apple-reviewer フォルダ配下のみ（`my_common_templates/` `apps/` `review_logs/` 等）
  - レビュー対象アプリのプロジェクトファイルは直接編集しない（調査はRead/Bash等の閲覧のみ）
  - 指摘・提案は必ずreview_logsの**「レビューサマリ」**セクションに記録する。**「対応サマリ」セクションには書き込まない**（作業エージェント専用）
- **作業エージェント**（レビュー対象アプリのプロジェクトフォルダで作業するエージェント）
  - 編集してよいのは自プロジェクトのファイル、および `review_logs/{アプリ名}/{日付}.md` の**「対応サマリ」セクションのみ**
  - `my_common_templates/` `apps/` やレビューサマリ部分は編集しない

## ライフサイクル

1. 審査エージェントが指摘・提案を見つけたら、「レビューサマリ」に提案書形式で記録する（会社の審査部が開発部に提案書を出すイメージ）
2. ユーザーが対応を承認したら、審査エージェントはAgentツールで対象プロジェクトのディレクトリに作業エージェントを派遣する（詳細は`../CLAUDE.md`の「作業エージェントへの委任」参照）。ユーザーが手動で別セッションを開いて対応してもよいが、派遣の方がフォルダを行き来せずに済む
   - 作業エージェントはコードを直し、対応結果を「対応サマリ」に記入する
   - 作業エージェントが判断に迷う点に当たった場合は、独断で進めず作業を中断して報告する。審査エージェントがその内容をユーザーに伝え、回答を得てから`SendMessage`で作業エージェントを再開させる
3. 審査エージェントは、対応サマリが記入済みだが`反映状況`が`未反映`の提案がないか確認し、内容をユーザーに要約した上で、一般化できるものは`my_common_templates/`へ、事実の更新は`apps/{アプリ名}.md`へ反映する。反映したら対応サマリの`反映状況`を更新する

## 記録テンプレ

```markdown
# {アプリ名} 審査ログ ({日付})

対象ブランチ: {ブランチ名}

## レビューサマリ（審査エージェント記入・このセクションのみ編集可）

### 提案1: {一言タイトル}
- 種別: 共通設計違反 / 新規共通設計提案 / 問題のある設計の修正要求
- 対象: {ファイル・画面等}
- 内容: {何が問題か、または何を提案するか}
- 根拠: {Apple公式ルール or my_common_templatesへのリンク}
- 提案内容: {具体的にどう直す/どう設計すべきか}

（複数ある場合は 提案2, 提案3 ... と続ける）

## 対応サマリ（作業エージェント記入・レビュー対象アプリ側で追記）

### 提案1への対応
- 状態: 未着手 / 対応中 / 対応済み / 誤検知（対応不要） / 保留
- 対応内容: {何をしたか。誤検知の場合はその根拠}
- 追加で見つかった問題（あれば）: {調査中に新たに発覚した問題}
- 関連コミット: {あれば}
- 反映状況: 未反映 / 反映済み（{日付}, {反映先ファイル}）

## 提出後の審査結果
- 承認 / リジェクト（理由） / （未提出）
```

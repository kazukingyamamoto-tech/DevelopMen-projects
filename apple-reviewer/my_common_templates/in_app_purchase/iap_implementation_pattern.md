# IAP実装の自分パターン

Apple公式ルールではなく、複数アプリで統一する自分のIn-App Purchase実装方針を記録する場所。
Apple公式ルールとの整合性は [../../in_app_purchase/](../../in_app_purchase/) 配下を参照。

### 1. 使用パッケージ・レシート検証の実装方針
**背景・意図:** クライアント側だけの検証は改ざん・詐欺に弱いため、Apple公式ルール（[../../in_app_purchase/receipt_validation_policy.md](../../in_app_purchase/receipt_validation_policy.md)）上もサーバー検証が前提。さらに「検証成功前に`completePurchase`を呼ぶ」実装は、一時的な通信エラー等で検証が失敗した際にストアのトランザクションキューから消えてしまい、ユーザーは支払い済みなのに権利が付与されず、しかも復元も効かないという致命的な不具合になる。この順序を守ること自体が最重要のバグ予防策。

**必須要件:**
- レシート検証はCloud Functions等サーバーサイドで行い、クライアントだけで判定しない
- `completePurchase`は検証成功が確認できた**後**にのみ呼ぶ。検証前に完了させない
- `pending`（ファミリー共有の承認待ち等）では`completePurchase`を呼ばず、後続で届く`purchased`を待つ。勝手に完了させると保留中トランザクションを潰してしまう
- `error`ステータスは`completePurchase`を呼んでキューをクリアしてからエラー表示する
- 価格表示用に取得した`ProductDetails`は、そのまま購入実行にも使い回す（表示用・購入用で別々に問い合わせると、Sandbox等で通貨・価格表示がタイミング次第でズレることがあるため）
- プレミアム等の権利判定は「Firestoreの特定フィールド（例: `is_premium`）」を正とし、判定ロジックを1箇所の関数に集約する（画面ごとに判定を書くと基準がズレる）

### 2. Restore Purchaseの実装方針
**背景・意図:** 「購入の復元」は機種変更・再インストール時にユーザーが自分から探して押すボタンとしてだけでなく、アカウント連携でuidが変わる瞬間にも自動的に必要になる（詳細は4番参照）。ボタン経由の復元しか用意しないと、連携直後に権利が反映されずユーザーが混乱する。

**必須要件:**
- 明示的な「購入の復元」導線を用意する（Apple公式ルール: [../../in_app_purchase/restore_purchase_flow.md](../../in_app_purchase/restore_purchase_flow.md)）
- アカウント連携によって別アカウントへ切り替わった場合は、ユーザー操作を待たずその場で`restorePurchases()`を自動的に呼び、切り替え後のアカウントにも権利を反映する

### 3. プロダクトID命名規則
**背景・意図:** プロダクトIDはBundle IDの下位互換で管理すると、ストア側の商品一覧やコード内の定数を見ただけでどのアプリのどの機能かが一目で分かり、複数アプリを横断して運用する際の取り違えを防げる。

**必須要件:**
- `{bundleId}.{機能名}`形式で命名する（例: `com.zetaiw.math100.removeads`）

### 4. 未ログイン購入とアカウント連携の標準フロー
**背景・意図:** 「サインアップしないと課金できない」制約は購入までの離脱要因になる一方、Firebase Cloud Functionsでのレシート検証には`request.auth`（uid）が必須で、何らかのFirebase Authユーザーが必要になる。この矛盾を「ユーザーに見せるUIなしの匿名認証」で解決し、購入のハードルを上げずに検証基盤の要件も満たす。ただし匿名uidは機種変更・再インストールで失われるため、購入後にアカウント連携を案内し、連携時に認証情報が既に別アカウントで使用済みという衝突ケースまで面倒を見て初めて実用に耐える。

**必須要件:**
- 購入ボタン押下時に未ログインなら`signInAnonymously()`を実行し、画面遷移やユーザー操作なしで匿名uidを確保してから購入フローに進む
- 購入完了後、機種変更・再インストール時に購入を引き継げるよう、Google/Apple等アカウントとの連携を案内する
- 連携には`User.linkWithCredential()`を使い、既存のuid（＝紐づく権利情報）を維持したまま認証方法だけを追加する
- 連携先の認証情報が既に別のFirebaseアカウントに紐づいている場合（`credential-already-in-use` / `email-already-in-use`）は、そのアカウントに`signInWithCredential()`でサインインし直し、`restorePurchases()`で購入情報を再検証してそちらに権利を反映する
- 上記フォールバック後に取り残される匿名アカウント側のFirestoreドキュメントは、実害のないデータの残骸として扱い、削除等の後始末をしない（[[data_storage_pattern]]の匿名ユーザー向け削除UI非表示の方針とは別軸の判断であることに注意: あちらは「削除ボタンを見せない」、こちらは「孤立データを追わない」）
- 別の課金アイテムを追加する場合も、購入処理の起点は必ずこの`ensureSignedIn`相当の匿名確保処理を経由させ、フローを分岐させない
- **自動`restorePurchases()`の適用範囲:** 上記の自動`restorePurchases()`呼び出しは、既存の別アカウントへ切り替わるフォールバック時（`credential-already-in-use`等）に限定する。真に新規のFirebaseアカウント作成時（初回サインアップ・プロフィール未作成時）には自動的に呼ばない。
  **背景・意図:** 新規アカウント作成のたびに無条件で自動復元すると、同一Apple ID配下で新しいFirebaseアカウントを作るたびに購入情報が何もせず伝播し、「アプリ内アカウントを跨いだ購入共有」を実質的に助長してしまう（Math_Practiceで2026-08-08に発覚）。Apple 3.1.1が求めるのは「復元ボタンの設置」「復元操作が正しく動作すること」であり、無条件の自動伝播までは求めていない（[../../in_app_purchase/restore_purchase_flow.md](../../in_app_purchase/restore_purchase_flow.md)参照）。ユーザー操作を起点とする復元導線（設定画面等の「購入を復元」ボタン、サインイン状態を問わず常時表示）を別途確保していれば、正規ユーザーの救済としては十分。
- **購入の逆引きインデックス設計:** 同一Apple ID/Google側の取引が複数のFirebaseアカウントに跨って復元されうる設計では、取引ID→uidの逆引きインデックスは「現在の所有uid」を1つだけ持つ単一フィールドとし、新しいuidが復元するたびに、直前の所有者から`is_premium`を剥奪し新しいuidへ移す「排他的所有権の移動（Transfer）」方式を採る（業界標準のRevenueCatのデフォルト挙動と同じ）。返金・剥奪処理は現在の所有uid1件に対して行う。アカウント削除時、自分が所有者であればインデックスドキュメントごと削除してよい（他アカウントとの共有状態は構造上発生しないため）。
  **背景・意図:** 初期実装（2026-08-08）では逆引きインデックスに関与した全uidを配列で保持し「全員が同時に権利を持ち続けられる」設計にしていたが（[[review_logs/Math_Practice/2026-08-08]]）、業界標準（RevenueCat）を調査した結果、これは一般的な期待（新しく復元した側が権利を持ち、元の側は失う）と異なることが判明した（[[review_logs/Math_Practice/2026-08-08_3]]）。Transfer方式なら、そもそも「同一Apple IDで新規アプリ内アカウントを作るたびに際限なく増殖する」という構造的懸念が発生しない（常に所有者は高々1人）。ただし、この方式では「1台の端末を家族で共有し複数プロフィールが同時にプレミアムでいてほしい」という用途には対応できない点はトレードオフとして残る。そのような用途を想定するアプリでは、uids配列方式を意図的に選ぶ判断もありうるため、一律にどちらが正しいとは言えない。

  **ファミリー共有（Family Sharing）を併用する場合の注意点:** Transfer方式を採用しつつファミリー共有にも対応したい場合は、App Store Server APIのトランザクション情報に含まれる`inAppOwnershipType`を確認し、`FAMILY_SHARED`（共有経由の取引）であれば既存所有者からの剥奪対象から除外し、単に復元したuidへ`is_premium`を付与するだけに留める分岐を設ける。
  **背景・意図:** ファミリー共有で家族に配布される取引は、`inAppOwnershipType`で「本人購入(`PURCHASED`)」か「共有経由(`FAMILY_SHARED`)」かを区別できるが、`originalTransactionId`自体は購入者本人のものが家族全員に共通する。そのため上記の分岐を入れずTransfer方式をそのまま適用すると、家族Aが復元して所有者になった直後に家族Bが復元した場合、同一`originalTransactionId`であるためBがAから所有権を奪う形になり、ファミリー共有が本来意図する「家族全員が同時に使える」状態にならず家族間で所有権の奪い合いが発生してしまう（Math_Practiceのレビューで2026-08-09に判明）。この分岐を実装しない場合、Transfer方式とファミリー共有は原則として併用不可と考え、ファミリー共有自体を不採用にする判断も合理的である（特に、アプリが1アカウント内で複数プロフィール/プレイヤーを作成できる別の仕組みを既に持つ場合は、ファミリー共有によるアカウント間共有のニーズ自体が薄れるため尚更）。

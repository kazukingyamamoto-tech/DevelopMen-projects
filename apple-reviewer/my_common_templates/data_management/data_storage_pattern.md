### 1. 採用するDB/ストレージの標準構成
**背景・意図:** サインアップを課金や利用開始の前提条件にすると離脱要因になる（[[iap_implementation_pattern]]の「未ログイン購入」と同じ考え方）。一方でクラウド同期・機種変更時の引き継ぎには何らかのアカウントが必要になる。この両立のため「まずローカルに保存し、サインインが確定した時点でクラウドへ移行する」という順序を標準とする。

**必須要件:**
- 初期状態ではSharedPreferences等ローカルストレージに記録を保存し、未ログインでも主要機能を使えるようにする
- Firebase Authでのサインイン（匿名含む）が成立した時点で、ローカル記録をFirestoreへ一括移行する専用サービス（例: `LocalDataMigrationService`）を用意する
- 再サインイン時にローカルとクラウド双方に未同期の記録がある場合は、片方を無条件で上書きせず、ユーザーに引き継ぎ方法を選択させる画面を挟む

### 4. アカウント削除UIの表示条件
**背景・意図:** Apple 5.1.1(v)が要求するアプリ内アカウント削除は、ユーザーがメール・SNS・電話番号等で能動的に「アカウントを作成」した場合が対象。匿名サインイン（`signInAnonymously()`等、ユーザー操作を伴わずバックグラウンドで発行されるもの）のみのユーザーはそもそも規制対象外であり、かつFirebase等クラウド側に削除すべきデータを持たない場合が多い。この状態のユーザーに削除ボタンを表示すると、規制上不要なだけでなく、`providerData`が空リストであることに起因する実装ミス（例: `providerData.first`での例外）でクラッシュする実例があった（[[review_logs/Math_Practice/2026-07-26]]参照）。

**必須要件:**
- 課金のみ行い、クラウド側にプレイデータ等を保存していない匿名ユーザーにはアカウント削除ボタンを表示しない
- 表示条件は「クラウドにユーザー起因のデータを保持しているか」を本質とし、実装上は `currentUser != null && !currentUser.isAnonymous` のように匿名判定でスコープする
- `providerData`等、匿名ユーザーでは空になり得るフィールドに対して `.first` 等の無条件アクセスをしない

### 5. Firestoreセキュリティルールの標準パターン
**背景・意図:** クライアントから送信された値をそのまま信頼すると、`is_premium`のような権利フラグをクライアント側から偽装して無料で有料機能を使われてしまう。また、Cloud Functionsが内部管理用に使うコレクション（購入トークンの逆引き等）は、そもそもクライアントが直接読み書きする理由がない。

**必須要件:**
- 全ての読み書きルールで`request.auth != null && request.auth.uid == <対象ドキュメントのuid>`を基本パターンとする
- 権利・課金状態を表すフィールド（`is_premium`等）は、ドキュメント作成時は「false以外を拒否」、更新時は「そのフィールドの変更を拒否」というルールでクライアントからの直接書き込みを禁止し、Cloud Functions（Admin SDK、ルールをバイパスする）経由でのみ変更可能にする
- Cloud Functionsが内部的にのみ使う逆引き・インデックス用コレクション（例: 購入トークン→uidの対応表）は、クライアントからは`allow read, write: if false`で全面的にアクセス禁止にする
- 上記のような「クライアントから読めない/直接書けないコレクション」を作った場合、そのuidに紐づくエントリはアカウント削除時にも削除対象に含める（[[review_logs/Math_Practice/2026-07-26]]で、削除漏れが見つかった実例がある）
- 逆引きインデックスが「取引ID→現在の所有uid」の単一マッピング（Transfer方式、[[iap_implementation_pattern]]の「購入の逆引きインデックス設計」参照）の場合、所有者は常に高々1人のため、自分が所有者であればそのuidに紐づくエントリ（ドキュメント）ごと削除してよい。他アカウントとの共有状態は構造上発生しないため、配列操作や「他要素が残る場合は残す」といった条件分岐は不要（[[review_logs/Math_Practice/2026-08-08_3]]参照）

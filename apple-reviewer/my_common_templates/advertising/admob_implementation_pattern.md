# AdMob実装の自分パターン

Apple/Googleの一般ルールではなく、複数アプリで統一する自分のAdMob実装方針を記録する場所。
Apple公式ルールとの整合性は [../../advertising/admob_policy.md](../../advertising/admob_policy.md) を参照。

### 1. 広告ユニットID・SDK初期化の管理方針
**背景・意図:** 広告ライフサイクル（初期化・ロード・表示・破棄）が画面ごとにバラバラに実装されると、「広告オフのはずなのに表示される」「破棄漏れでメモリリークする」といった事故の温床になる。1箇所に集約し、画面側は状態を意識せず呼び出すだけにすることでこれを防ぐ。

**必須要件:**
- 広告管理は`AdManager`のようなシングルトンクラスに一元化する
- Web/対象外プラットフォームでは広告機能自体を無効化するガードを設ける（`kIsWeb`や`Platform.isAndroid/isIOS`判定）
- `maxAdContentRating`は`MaxAdContentRating.g`（全年齢向け）をデフォルトとし、成人向けコンテンツを扱うアプリの場合のみ個別に緩める（背景: Gは最も制限が厳しい安全側の値で、全年齢向けアプリの標準として問題が起きにくいため）
- 課金による広告オフ状態は、アプリ内のクラウド上のプレミアムフラグ（例: Firestoreの`is_premium`）を正とし、起動時に反映する（背景: メモリ上のフラグだけだと再起動やマルチデバイスで状態が食い違うため）

**条件付きデフォルト（アプリごとに前提を確認すること）:**
- `MobileAds.instance.updateRequestConfiguration`の`tagForChildDirectedTreatment` `tagForUnderAgeOfConsent`は、**そのアプリがApp Store ConnectでKidsカテゴリとして出品されておらず、かつ子供を主対象・前面に押し出したマーケティングをしていない**ことを確認できた場合に限り`no`をデフォルトにしてよい
- Kidsカテゴリで出品する場合や、子供向けを前面に出すアプリの場合は逆に`yes`にする必要があるため、このデフォルトを機械的に流用せず、レビュー時に毎回`apps/{アプリ名}.md`のカテゴリ情報と照らして判定する

### 2. 広告フォーマット・配置の標準方針
**背景・意図:** 広告の読み込み中/失敗時にレイアウトが動くとユーザー体験を損ない、誤タップも誘発しやすい。また表示可否の判定を呼び出し箇所ごとに書くと、チェック漏れで「広告オフのはずが表示される」事故につながる。これらを配置・呼び出しのルールとして固定化する。

**必須要件:**
- バナー広告は読み込み前後でレイアウトが変わらないよう、広告サイズ分の枠を常に確保しておき、ロード完了時に中身だけ差し替える
- インタースティシャル/リワードは「事前ロード → 表示 → dispose → 即再ロード」のサイクルを徹底する（背景: 表示タイミングで読み込み待ちが発生すると体験を損なうため、常に次の広告を準備しておく）
- インタースティシャルには最低表示間隔（クールダウン）を設け、前回表示から一定時間（目安90秒。1ラウンドの所要時間が短いアプリほど短時間で連続表示されやすいため、アプリのコアループの長さに応じて調整する）未満の場合は表示をスキップする（背景: 区切りごとに毎回表示すると短時間の連続表示になり、UXを損なうだけでなく[../../advertising/ad_placement_ux_rules.md](../../advertising/ad_placement_ux_rules.md)の「短時間での連続表示を避ける」要件にも抵触しうる。スキップ時も遷移コールバックは通常どおり呼び、画面遷移自体は妨げない）
- 広告の表示可否は`isAdEnabled`のような単一のゲートに集約し、各呼び出し箇所で個別に判定を書かない
- 広告の開始・終了・（リワードなら）獲得完了をFirebase Analytics等に毎回イベントとして記録する（背景: 広告在庫の欠品・表示エラー率などを後から追跡できるようにするため）

### 3. dev/prod環境での広告ID切り替え方針
**背景・意図:** 広告ユニットIDをコードにハードコードすると、テスト広告IDと本番広告IDの切り替え忘れ・混同事故（[../../advertising/admob_policy.md](../../advertising/admob_policy.md)の運用分離要件）が起きやすく、無効なトラフィックとして検知されるリスクがある。

**必須要件:**
- 広告ユニットIDはOS・フォーマットごとに`--dart-define`（例: `ADMOB_BANNER_UNIT_ID_ANDROID` / `_IOS`）で注入し、コードに直書きしない
- 広告ユニットIDの`String.fromEnvironment`には、dart-define未指定時でも安全に動作するようGoogle公式の公開テスト用広告ID（例: `ca-app-pub-3940256099942544/6300978111`）を`defaultValue`に設定する（背景: [../flutter_project_structure.md](../flutter_project_structure.md)3番参照。テスト広告IDは全アプリ共通のGoogle公式固定値のため直書きしても情報漏洩リスクはない）
- ATTの同意結果に応じて、非パーソナライズ広告リクエスト（`AdRequest(extras: {'npa': '1'})`）に切り替える（背景: ATTで許可されなかった場合にパーソナライズ広告を要求するとApple/Googleのポリシー違反になるため）

### 4. ATTプロンプトの表示タイミングとプレプロンプト設計
**背景・意図:** アプリ起動直後や同意画面直後など、ユーザーがアプリの価値を何も体験していない段階でATTシステムダイアログをいきなり表示すると、同意率が下がるだけでなく文脈のない唐突な要求になる（[../../apple_guidelines/05_legal/att_tracking.md](../../apple_guidelines/05_legal/att_tracking.md)項目2）。一方でシステムダイアログの前に独自の説明画面（プレプロンプト）を挟むことは許容されるが、内容によっては誘導とみなされるため文言には注意が必要（同項目3）。

**必須要件:**
- ATTシステムダイアログの呼び出しは、アプリ起動直後（splash画面等）ではなく、**ユーザーが最初に主要機能を一度体験した後の区切りのタイミング**（例: 1プレイ分完了後の結果画面到達時）まで遅らせる
- 一度要求したら再度表示しないよう、`hasRequestedAtt`のような永続化フラグで初回のみに限定する
- ATT結果が出るまでの間の初期値は非パーソナライズ広告（`setPersonalizedAds(false)`相当）とする
- システムダイアログの直前に独自のプレプロンプト画面を挟み、トラッキングの目的（例: 関連性の高い広告表示のため）と、拒否してもアプリの機能に制限がないことを正直に説明する
- プレプロンプトの文言は、同情・応援等トラッキングの目的と無関係な訴求で同意を誘導する内容にしない。「いつでも設定から変更できる」等のコントロール感を伝える一文を添えると、内容の正確性を保ったまま安心感を出せる
- プレプロンプトは「次へ」相当のボタン1つのみとし、閉じる/キャンセル導線は設けない（`barrierDismissible: false`等でタップ外・バック操作による閉じるも抑止する）。実質的な拒否権はこの後表示される本物のOSダイアログ側で担保されるため、プレプロンプト自体に中途半端な離脱経路を作らない

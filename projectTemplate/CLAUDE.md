# CLAUDE.md

# プロジェクト概要

本プロジェクトは、iOSおよびAndroid向けのネイティブアプリ開発プロジェクトです。
あなたは、世界最高レベルの技術力と、Apple/Googleの審査基準・法的コンプライアンスに精通した「シニア・ネイティブアプリエンジニア 兼 厳格なQAテスター」として振る舞ってください。

## 1. アーキテクチャとコーディングルール（DRY原則の徹底）

- コードの重複を絶対に避けること。新しい機能（特に計算、通信、データ処理など）を実装する前には、必ず `lib/utils/_AI_INDEX.md` を読み込み、既存の処理を再利用できないか確認すること。
- 関数名は、短さよりも「何をしているかが明確にわかる情報量の多さ（極端に長く説明的な英語のキャメルケース名）」を最優先すること（例: `fetchUserProfileFromDatabaseAndCalculateAgeBasedOnBirthday`）。
- 画面（UI）のコンポーネント内に、複雑なビジネスロジックやデータフェッチ処理を直接記述しないこと。純粋な処理は `lib/utils/` ディレクトリに分離すること。`lib/ui/` には見た目のコード（Widget）のみを書くこと。

## 2. 環境変数とセキュリティ

- テスト環境と本番環境の切り替えをスムーズにするため、環境に依存する値（API URL、Google SignInの `serverClientId` など）は絶対にコード内にハードコード（直書き）しないこと。
- 必ず `.env.prod` ファイル（本番用）から環境変数を読み込む形で実装すること。外部パッケージ（flutter_dotenvなど）は使用せず、Flutter標準の `--dart-define-from-file` を使用する。
  - **設定ファイルの配置**: プロジェクト直下に `.env.prod`（本番用）を作成して変数を管理する（`.env.example` をコピーして作成し、実際の値はGit管理外）。本番リリース前には必ず `.env.prod` の値を実際の本番ID・URLに置き換えること。
  - **読み取り方法**: コード内からは `String.fromEnvironment('変数名', defaultValue: '...')` で読み取り、dart-defineを渡さない場合でも安全に動作するデフォルト値（広告ユニットIDであればGoogle公式の公開テスト広告ID等、外部に公開しても問題のない値）を必ず設定すること。
  - **実行・ビルドコマンド**: 開発時は素の `flutter run` でよい（各値はコード側の `defaultValue` により安全なテスト用の値へ自動フォールバックするため、開発用envファイルは不要）。本番ビルド時は `flutter build ... --dart-define-from-file=.env.prod` のように本番用ファイルを指定する。
- OAuthの `clientSecret` などの機密情報は、絶対にアプリ内に含めないこと。

## 3. テスト駆動と品質保証（最重要）

- 既存機能を修正、または新機能を追加する際は、必ず `docs/test_specs/` フォルダ内の関連するテスト仕様書（マークダウン）を確認し、既存の仕様を破壊しないように実装すること。
- 実装が完了したら、AI自身の判断でテスト仕様書を最新の状態にアップデート（または新規作成）すること。正常系だけでなく、通信エラーやデータ欠損などの異常系（エッジケース）の挙動も必ずテスト仕様書に含めること。

## 4. ネイティブアプリ特有のコンプライアンス（審査対策）

- カメラ、写真フォルダ、位置情報、トラッキングなどのユーザーデータにアクセスする機能を実装する際は、技術的な実装の前に、必ずユーザーから権限を取得する同意フロー（ATTダイアログやパーミッション要求）をUIに組み込むこと。
- アプリストアの審査でリジェクトされる可能性のある実装（利用規約の同意漏れ、退会機能の欠如など）に気づいた場合は、実装前に人間に警告・提案すること。

## 5. Gitブランチ運用と強制自動コミット・タグ付けルール

本プロジェクトでは、スピードを最優先するため複雑なブランチ運用は行わず、基本的に `dev` ブランチのみで開発を進行します。AIはコードを破壊するリスクを防ぐため、以下の手順を厳守してください。

- **使用するブランチ構成**:
  - `dev`: メインの開発・作業ブランチ。AIによる実装はすべてここで行う。
  - `main`: 安定版の本番ブランチ（デプロイ用）。ここには絶対に直接コミットしないこと。

- **開発中機能のmain除外ルール**:
  `dev` ブランチにのみ実装されており、まだ `main` へ反映してはいけない機能（実験的機能・未完成機能）は、以下の方法で明示すること。
  - **関数名でのマーキング**: 該当する関数名の末尾に `DevOnly` を付与し、mainに未反映であることが名前から一目でわかるようにする（例: `sendPushNotificationToUserDevOnly`）。ファイル全体が開発中の場合はファイル名にも同様に付与する。
  - **`lib/utils/_AI_INDEX.md` への記載**: 該当する関数・ファイルを「開発中機能（main未反映）」セクションに追記し、対象・理由・関連する開発中機能を記録する。
  - **AIによるmainへの自動マージ時の除外**: `dev` から `main` へAIがマージを行う際は、`DevOnly` が付いた関数・ファイルを含む変更をマージ対象から除外すること。本番用コードと同一ファイル内に混在していて機械的に除外できない場合は、マージを実行せず人間に確認を求めること。

- **【最重要】実装前の強制自動セーブ（クリーンチェック）**:
  AIは新しい機能の実装やコードの修正指示を受けた際、**実際のコード変更に取り掛かる前に、必ず `git status` 相当の確認（ワーキングツリーのチェック）を行うこと。**
  もし未コミットの変更（差分）が残っている場合は、**次の作業に移る前にAI自身で差分（git diff）の内容を分析・要約し、適切なコミットメッセージを自動生成してコミットを完了させること。** ステージを完全にクリーンな状態にしてから新しい作業を開始すること。

- **自動コミットメッセージの命名規則**:
  後からログを遡りやすくするため、以下のフォーマットでコミットすること。
  フォーマット: `chore(ai-save): [自動要約] 〇〇の処理追加や修正内容`

- **コミット後の自動push**:
  `dev`ブランチへのコミットが完了したら、そのたびに`git push origin dev`までセットで行うこと（pushし忘れによる作業の取りこぼしを防ぐため）。
  pushが失敗する場合（リモート側にローカルに無いコミットがある等）、force pushは行わず人間に確認すること。`main`ブランチへのpushはこのルールの対象外とし、7章の手順に従うこと。

- **リリース時のスナップショット（Tag機能の活用）**:
  バージョン管理用のブランチ（`ver1.0.0`等）は作成しない。
  本番環境（`main`）へのリリースが完了したタイミングで、AIは必ず最新のコミットに対して**注釈付きタグ（Annotated Tag）**を付与すること。
  フォーマット: `v1.0.0` （タグメッセージにはそのバージョンの主要な変更点を要約して含めること）

## 6. AIとの基本業務フロー（Standard Operating Procedure）

新しい機能の追加や改修を行う際は、AIは勝手にコードの記述を開始せず、必ず以下のステップ順に沿って人間と対話しながら進行すること。

- **Step 1: 意図の確認と調査**
  人間の要望を受け取ったら、まずは `lib/utils/_AI_INDEX.md` や既存のコードベースを検索し、影響範囲や再利用できる関数がないか調査する。
  正規開発の初期構築など、人間から提示された構成書（アプリの画面構成をまとめたラフな樹形図）をもとに実装を進める場合、構成書は詳細な仕様書ではなく出発点として書かれているため、該当ノードの挙動や計算ロジックに不明点があれば、テスト仕様書の作成に入る前に人間に確認し、認識をすり合わせること。
- **Step 2: テスト仕様書の作成・更新（コード記述前の必須タスク）**
  コードを書く前に、必ず `docs/test_specs/` 内のマークダウンを更新、または新規作成すること。
  **※新規作成の際は、必ず同フォルダにある `_TEMPLATE.md` のフォーマット（正常系・異常系・OS固有・審査確認）を厳格に守って記述すること。**
  作成後、人間に「このテスト仕様で実装に進んでよいか」の承認を求めること。
- **Step 3: 強制自動セーブ（Gitクリーンチェック）**
  人間の承認が出たら、実装に入る前に `git status` を確認。差分があれば自動要約してコミットし、ステージをクリーンにする（5章を参照）。
- **Step 4: 実装とリファクタリング**
  クリーンな状態からコードの実装を開始する。UIとビジネスロジックの分離、長文の関数名、DRY原則を守ること。
- **Step 5: 完了報告と審査確認**
  実装が終わったら、追加した機能がApple/Googleの審査基準や法的ルール（パーミッション同意など）に違反していないかAI自身で最終チェックを行い、人間に完了を報告する。
  あわせて、Step 2で作成・更新したテスト仕様書のチェック項目のうち、AI自身で検証できるもの（`flutter analyze`、ビルド、curl等によるエンドポイントの疎通確認、ログの確認など）は実際に検証し、確認できた項目にチェックを入れること。実機でのストア決済など、AIだけでは検証できない項目は未チェックのまま残し、人間に何が未検証かを明確に報告すること。

## 7. 特殊業務フロー（mainとdevの扱い）

`main`と`dev`は独立した履歴として扱い、**`main`を`dev`のfast-forward先にはしない**（ブランチ間で意図的に異なる値や`DevOnly`機能などの状態を許容する設計のため）。両ブランチを揃えるための`git merge`は行わない。

- **mainへの移植（プロモーション）作業**:
  ユーザーから「mainへの反映」を指示されたら、AIは以下の手順で行う。
  1. `git cherry -v main dev`で、`dev`にあってまだ`main`へ適用されていないコミットを洗い出す（内容が既にmainへ適用済みのコミットは自動的に除外される）。
  2. その中から`DevOnly`が付いた関数・ファイルのみを含むコミットを除外する。本番用コードと同一ファイル内に混在し機械的に除外できない場合は、cherry-pickせず人間に確認を求める（5章の除外ルールを参照）。
  3. `.claude/settings.local.json`・`.vscode/launch.json`等、ローカル開発者環境固有の設定ファイルは移植対象から除外する。
  4. 残ったコミットを古い順に`git cherry-pick`で`main`に適用する。
  5. 完了後、5章の既存ルールどおり`main`の最新コミットに注釈付きタグ（`v1.0.0`等）を付与する。

## 8. 保留事項の記録ルール

- 実装・テスト・設定作業などについて、ユーザーが「今は対応しない」「保留する」と判断した事項は、`docs/PENDING_DECISIONS.md` に記録すること。iOS/Android/共通で区分し、対象・保留の理由（Why）・現状・再開条件を記載する。
- 記録・更新したら、5章の既存ルールどおりコミット・`git push origin dev`まで行い、GitHub上でも常に参照できる状態を保つこと。
- 保留にしていた事項が解決した場合は、対応完了の報告と合わせて `docs/PENDING_DECISIONS.md` から該当エントリを削除すること（放置して情報が古びるのを防ぐため）。

## 9. apple-reviewerナレッジベースとの連携

本プロジェクトは `../apple-reviewer/` の審査ナレッジベースと連携している（このプロジェクトが `apple-reviewer` フォルダと同じ階層に配置されていることが前提）。

- 審査エージェント（apple-reviewer側）からのレビュー指摘・提案は `../apple-reviewer/review_logs/{このプロジェクト名}/{日付}.md` の「レビューサマリ」に記録される。
- 本プロジェクトのAIが対応する際は、対応結果を同ファイルの**「対応サマリ」セクションにのみ**追記すること（「レビューサマリ」や`../apple-reviewer/`配下の他のファイルは編集しない）。
- 状態（未着手/対応中/対応済み/誤検知/保留）・対応内容・追加で見つかった問題・関連コミットを記入する。`反映状況`欄は審査エージェント側が更新するため触れない。
- 記録・更新したら、5章の既存ルールどおりコミット・pushまで行う。
